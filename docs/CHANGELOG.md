## v0.1 · MVP（2026-09-16）

**目标**：用一条流水线替代人工编辑，每天为三个市场产出可信的金融科技要闻。

- 端到端流水线：RSS 采集、同一事件合并、大模型选题、抓取原文、写作、事实核查、编辑审核、发布到 Telegram
- 基于**原文全文**而不是 RSS 摘要写作；同一事件的多个来源合并为一条
- 核查不通过时先修复一轮，而不是直接删除
- 只认编辑在真实草稿消息上的批准，旧消息或测试预览上的按钮无效
- 兼容模型不规范的输出（格式回退、字符串形式的数字和布尔值）
- 安全审计：只抓取和发布 http/https 链接；日志、状态和消息中自动隐去密钥
- 每次提交自动运行单元测试（CI）

## v0.2 · 适配免费额度（2026-09-16）

**问题**：免费层每个模型每天只有约 20 次请求，高峰期还经常返回"过载"；GitHub 的定时任务会延迟。

- 不同步骤分配给不同模型，让每个模型都落在自己的免费额度内
- 遇到"过载"时重试并依次换用备用模型，报告中写明换模型的原因
- 应对定时任务延迟，上线日期推迟一天到 09-17，先把稳定性做好

## v1.0 · 正式上线（2026-09-17）

- 中文、英文、俄文三个频道开播
- **auto / manual 双模式**：auto 下草稿送达编辑、可一键否决，不操作则按时发布；manual 下必须人工批准；在机器人里用命令切换
- **幂等唤醒**：外部调度器唤醒机器人，机器人只做当下该做的事，多唤醒一次也不会重复发帖

## v1.1 · 不重复、准时（2026-09-28）

**问题 1**：同一事件会隔天重复出现，例如交易所被盗的新闻连续两天出现。根因是只按链接去重：第二天其他媒体换了链接和标题报道同一事件，模型也不记得之前发过什么。

- 选题模型能看到近 10 天已发布的内容，并标记重复事件；代码再按标题相似度比对
- 全量复查历史帖子，从三个频道中清理了 **31 处重复**：直接编辑已发布的帖子，自动重新编号、修正话题标签

**问题 2**：频道写着 08:30，实际约 08:43 发出，而且每天时间不同。

- 外部调度器在发布前 1 分钟唤醒机器人，机器人等到整点分钟再发送
- 决策前先核算 GitHub Actions 免费额度，并清理了每月约 330 分钟的冗余定时任务
- 结果：平均延迟从 11.8 分钟降到 **0 分钟**

**新功能**：每周一发布「一周回顾」，按要闻、交易、监管、趋势分栏，每行链接回原帖。

## v1.2 · 质量护栏升级（2026-10-05 至 10-06）

**问题**：上线一周后复查全部帖子，又发现 3 条新的重复。数据显示它们全部出现在主模型过载、由轻量模型 Flash Lite 选题的日子，它对"不要重复"这类指令遵循得更差。

- 核查环节增加**第二道重复检查**，选题漏掉的重复在这里拦下
- **选题环节等待主模型**，最多 3 轮，只有最后一轮才用 Flash Lite；只在选题环节等待，因为"过载"响应似乎也计入配额
- 备选新闻从 2 条增加到 3 条，被拦下的条目由备选补位
- 结果：第二道检查上线 3 天拦截 **5 条重复**

## v2.0 · 可度量（2026-10-09）

**目标**：从"感觉还行"变成可以追踪的数字。

- **运行指标** `metrics`：准点率、各道护栏的拦截次数、降级率、请求与 token 用量；旧草稿从质量报告中回溯
- **离线评测** `eval`：对已发布帖子做确定性检查，不调用模型；首次运行发现 2% 的条目超出提示词中的长度限制
- **在线评测** `eval-live`：盲评的 LLM-as-judge A/B，使用另一个 Google 项目的 API key，不占用日报的免费额度
- **「重写」按钮**：编辑用一句话提出修改，AI 只能使用原有来源重写，改动重新经过全部护栏，没通过就保留原文
- **用量记录**：每次请求的结果与 token 按模型、按步骤记录到每期草稿

## v2.1 · 评测驱动的提示词迭代（2026-10-09）

- 首次在线评测显示"为什么重要"是最弱的维度，裁判多次指出套话；还发现一处把"同意建立"写成"已建立"的时态错误
- 写作提示词新增规则：点明**谁**受影响、**如何**受影响，禁止套话，给出三组"弱 / 强"示例；计划保持将来时
- 对照实验：三个频道 63 条新闻，新旧提示词各写一遍，裁判盲评；"为什么重要" 4.2 → 4.9，准确性持平，详见 README「评测体系」
- 把 GitHub Actions 的运行环境固定为 Ubuntu 24.04，避免 10 月 19 日的镜像切换影响早间发布

## v2.2 · 应对模型下线（2026-10-11）

**问题**：Google 于 10-09 下线 Gemini 3.7 Flash，并把它的请求静默重定向到 3.8 Flash。选题与核查（3.7）和写作（3.8）实际上变成了同一个模型，"写和查分离"失效。

- 选题、核查和评测裁判切换到 3.6 Flash，3.5 Flash 作为下一个备用，保持写作与核查由不同模型完成、各用各的免费额度
- **自动发现静默重定向**：核对每次请求实际应答的模型，与请求的模型不一致时在质量报告中提示，不必等官方邮件

## v2.3 · 周度指标快照（2026-10-11）

**问题**：草稿只保留 14 天，`metrics` 只能看到最近两周，无法回答"这个月比上个月好还是差"。

- 每周一由定时任务自动运行 `metrics`，保存最近 7 天的指标快照，无需人工触发
- 报告中新增周度趋势表：准点、修正率、拦截率、代码校验占比、降级率、每期请求与 token、付费层估算
- 快照长期保留，指标可以按周追踪

## v2.4 · 每期都是完整的 7 条（2026-10-12）

**问题**：10-12 中文频道只发出 6 条。主模型过载，写作降级到 Flash Lite，它在 10 条候选（7 条 + 3 条备选）里只写了 7 条，核查又拦下 1 条译名错误。复查近两周：42 期中有 4 期少于 7 条，原因都是高峰期降级。

- **补写遗漏条目**：写作模型漏写时，只针对漏掉的条目再请求一次，补写内容同样经过全部护栏；在线评测采用同样的逻辑，保证裁判比较的是完整样本
- **自动补选一轮**：核查后草稿仍不足 7 条时，在送达编辑之前自动再做一轮选题、写作和核查：第一轮用过的文章不再使用，草稿中的新闻视为已发布，避免同一事件重复；补足后草稿照常送审，全程无需人工介入
- **成本口径修正**：付费层估算原先把便宜得多的每周回顾也算进了"每期成本"，导致结果偏低；改为只统计每日简报，每周回顾单独计算
