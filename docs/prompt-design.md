# 提示词设计

> 提示词原文见 [`prompts/`](../prompts)。三个频道共用同一套模板，语言、受众、编辑侧重、话题标签等通过变量注入。

## 总体设计

| 原则 | 做法 |
|---|---|
| **一个提示词只做一件事** | 选题、写作、核查、修复、一周回顾分为 5 个提示词，各自可以单独测试和替换模型 |
| **结构化输出** | 每个步骤都用 JSON Schema 约束输出，代码可以直接解析和校验，不依赖模型"自觉"遵守格式 |
| **写和查分离** | 写作与核查默认由不同模型完成，避免模型"自己检查自己" |
| **把护栏写进输出格式** | 写作时必须输出逐字引用（`source_quotes`），让后续代码校验有据可查 |
| **低温度** | `temperature: 0.3`，新闻场景优先稳定和准确，而不是创意 |
| **一份模板，多个市场** | `{{LANGUAGE}}`、`{{AUDIENCE}}`、`{{FOCUS}}`、`{{HASHTAGS}}` 等变量按频道注入 |

## 五个提示词

| 提示词 | 输入 | 输出 | 设计要点 |
|---|---|---|---|
| `selector.md` 选题 | 80 条候选、近期已发布内容 | 7+3 条新闻、合并的同一事件、`repeat_of` 标记 | 严格定义"什么算金融科技"；用正反例划清边界；明确"什么算同一事件" |
| `editor.md` 写作 | 选中新闻及原文全文 | 标题、摘要、为什么重要、来源、逐字引用、话题标签 | 只用原文事实；字符上限；禁止夸张修饰；要求附引用 |
| `verifier.md` 核查 | 写好的条目、原文、近期已发布内容 | 每条是否可发布、问题清单、`repeat_of` | 逐项核对事实、状态、角色、术语；同时做第二道重复检查 |
| `repair.md` 修复 | 未通过的条目、问题清单、原文 | 修正后的条目 | 只改被指出的问题；改不了就删掉相关内容 |
| `weekly.md` 一周回顾 | 本周已发布的条目 | 分栏要点 | 只能使用本周已发布的内容，不引入新事实 |
| `rewrite.md` 重写 | 编辑的修改要求、整期条目、原文 | 每条的新版本或删除标记（`keep`） | 只做被要求的修改，其余条目逐字不变；要求超出来源时保持原样 |
| `judge.md` 评测裁判 | 同一新闻的 A/B 两个版本与来源 | 四个维度 1–5 分与问题清单 | 盲评，不假设哪个更好；出现无依据事实时准确性最高 2 分 |

## 针对金融新闻的幻觉类型

通过线上问题总结出的高风险错误类型，被逐条写入写作和核查提示词：

| 错误类型 | 例子 |
|---|---|
| 状态混淆 | "宣布"写成"完成"；"待批准"写成"已批准"；"拟议规则"写成"最终规则" |
| 角色混淆 | "需要监管批准"写成"获得监管支持"；"投资方"写成"所有者" |
| 术语替换 | 把一个术语替换成更宽泛或不同的术语，例如 "money-management products" 译成"财富管理" |
| 凭空修饰 | 原文没有的"超级应用""独角兽""领先的""最大的" |
| "为什么重要"夹带新事实 | 解读部分出现原文没有的数字、日期、合作或计划 |

## 重复事件的定义

"不要重复"是一个模糊指令，模型很容易理解偏差。因此在提示词中给出了明确的判定规则：

**算作同一事件（不能再发）：**
- 数字更新或细节补充，例如同一次黑客事件先报 3.52 亿美元、后报 3.875 亿美元
- 围绕该事件的反应、评论、分析与后续讨论
- 其他媒体或次日对同一公告的转述

**不算重复（可以发）：**
- 之前宣布的交易现在完成或被叫停
- 诉讼被提起或判决
- 监管机构采取新的、独立的行动

拿不准时，按重复处理。

## 迭代方式

- 每次提示词修改都伴随单元测试，测试使用模拟模型，验证解析、校验和流水线逻辑
- 线上问题会被归类，再变成提示词中的明确规则或正反例
- 修改提示词后运行 `eval-live`：用最近 3 期作为黄金样本，盲评对比新旧版本，与上一次评测结果比较
- `eval` 离线检查每天的实际产出：例如发现 2% 的条目超出提示词中的长度限制
